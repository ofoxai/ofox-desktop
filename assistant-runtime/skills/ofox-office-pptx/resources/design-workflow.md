# Page planning and exported-deck review

This Ofox workflow is written independently from public evidence. It is separate from a visual theme, a layout library and an export engine. It includes no closed-source code, configuration, prompt, private template or sample.

1. Select a style by audience and task, then inspect its recipe and coverage. The public [Beautiful HTML style metadata](https://github.com/zarazhangrui/beautiful-html-templates/tree/e5e204fb1f3b06290846e7dcd7aceddabeceec8c/templates) illustrates distinct type hierarchy, density and composition. Preserve those relationships when choosing system-font substitutes; do not imply the upstream font binary was licensed or embedded.
2. Plan each page independently: claim; evidence with source; relationship (sequence, comparison, quantities, hierarchy); dominant visual; composition; reading order; density; native editing requirements. Read the claims in order before drawing. The public [make-a-deck workflow](https://github.com/manalkaff/opendesign/blob/cecd9bb6b59408cb96a3974449b8e6ef9f5b17bb/skills/make-a-deck/SKILL.md) provides a workflow reference, not an included engine or template library.
   In the frozen plan give every page its `pageKind` from the chosen style's page kinds and vary them: a third consecutive page of one kind needs a stated `continuity` reason. List each number, capability, result or benefit a page states in `facts` with its source; an `illustrative` value is labelled as an example on the page and a `proposed` item as a proposal, never as an established fact. An image visual states `placement`, `textZone` and `aspect`, so the picture is composed for its region and leaves the title and text clear; one `imageStyle` sentence keeps every generated image of the deck in the same look. These rules adapt ideas from PPT Master (image region, quiet zone, one deck rendering, rhythm), Presenton (an image bound to its page slot and size) and PPTAgent (a review tied to the current artifact); see the pinned record in `docs/superpowers/research/2026-11-11-ppt-public-workflow-reuse.md`. No upstream text or code is copied.
3. Generate using the existing engine. Text, shape/connector relations, native charts with data, and bounded OMML are separate object types. HTML/CSS layouts do not automatically become native PPTX. A rendered page screenshot is an image; arbitrary SVG and matplotlib figures currently remain raster images.
4. Review the exported PPTX, because export can alter fonts and geometry. Inspect completeness and qualifications, argument order, distinct composition, reading order, clipping, legibility, charts and formula rendering. Use reported issues plus the overview; no image access means visual review is unavailable. [PPTAgent's pinned export contract](https://github.com/icip-cas/PPTAgent/blob/9dacac53ac9ef39346461063df729396551d929e/skills/pptagent/references/task-contract.md) supports checking both source and exported deck and invalidating stale review after changes. Ofox uses its existing preview pipeline; it does not import that project's browser workflow.
5. Fix actual problems within the host's preview/retry limits (two previews per reply), and review the changed output. Bind review notes to the current artifact, never an earlier export. Deliver under one name and state unresolved issues. Existing automatic delivery of the last preview is preserved.

Quality acceptance needs evidence from equal-content A/B/C/D trials, not the number of source folders. Record facts, page count, language, density, model/engine/source versions, elapsed time and measured tokens. Keep estimated costs separate from billed amounts. Test native editing by changing text, chart data and formula structure, saving and reopening in the target application; XML object presence is structural evidence only. Cross-platform acceptance requires native tests on each OS.
