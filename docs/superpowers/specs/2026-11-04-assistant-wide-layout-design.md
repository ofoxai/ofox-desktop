# 全屏时的导航与助手布局（Fizzy #1460 的 04、05）

## 为什么做

本机试用反馈：全屏时助手页又空又散。顶部导航只占中间一小段，对话区被一圈圆角外框包住，13px 的字和 26px 的按钮放在 1500px 宽的屏幕上，四周大片空白。用户希望全屏时像 ChatGPT / Codex 桌面版那样：导航放在左边，对话区占满，字和按钮更大，页面饱满。窗口缩小时保持现在的样子。

## 目标

- 窗口宽时，整个 app 的页面导航（工具、会话、资源库、用量、助手）从顶栏移到最左边一条细的图标栏，顶栏不再显示。
- 宽布局下的助手页是图标栏、对话列表、对话区三栏，对话区不再有外框，内容更宽，字和按钮放大一号。
- 窄窗口时，所有页面和现在一模一样（截图见 #1460 的讨论：顶部导航，助手是带外框的列表加对话面板）。
- 宽窄之间随窗口大小自动切换，不用设置。

## 不做的

- 不改其他页面（工具、会话、资源库、用量）自己的内容排版。宽布局下它们只是换成左侧导航，内容占满图标栏右边的宽度。
- 不新增设置项，也不提供手动切换宽窄布局的开关。
- 不改对话、生成、用量的任何行为，只改排版。
- 不做 Windows、Linux 的自定义标题栏。这两个平台仍用系统标题栏。

## 反目标（技术上能用也算失败）

- 窄窗口和现在不一样，哪怕只差几个像素。
- 宽布局下仍然空荡：对话区窄窄一条在中间，左右大片空白。
- 切换宽窄时丢掉正在输入的草稿、正在进行的回复、滚动位置或展开的对话列表状态。
- macOS 的红绿灯按钮压住图标栏的内容，或者窗口在宽布局下无法拖动。

## 约束

- Tauri 2 应用。macOS 用 `titleBarStyle: "Overlay"`，红绿灯画在 `AppHeader` 上（位置 14,17，左边留 78px），整块 header 用 `data-tauri-drag-region` 拖动窗口。宽布局拿掉顶栏后，红绿灯和拖动区域要由图标栏和对话区顶部来承担。
- 页面导航现在在 `src/components/shell/AppHeader.tsx`（`SegmentedNav` + `SHELL_PAGES`，右侧还有 `UpdatePill`、刷新、设置），页面面板在 `src/components/console/ConsolePage.tsx`。各页面面板是 `role="tabpanel"`，导航是它们的 tab，宽布局下保持同样的可访问性关系。
- 助手页在 `src/components/assistant/AssistantPage.tsx`，对话列表是 `AssistantSidebar`（可收起，状态存在 `ofox.assistant.sidebarCollapsed`）。
- 字号是 `tailwind.config.cjs` 里的固定 px 刻度（`ui` 13px、`ctl` 12px、`note` 11px 等），全 app 共用。
- 所有可见文字走 i18n（中、英、日）。项目是开源的：不提 ofox-studio，不照搬闭源代码。
- 每次提交要通过 typecheck、Prettier、前端单测；动到 Rust 时还有 cargo fmt、clippy、测试。

## 用户定下来的

- 窄窗口：和现在一样（顶部导航；助手是带外框的列表加对话面板）。
- 全屏：用草图 B。最左一条细的图标栏放页面导航，旁边是助手的对话列表，再右边是对话区。切到其他页面时只剩图标栏和那个页面。
- 全屏时要更饱满：调整字号、按钮大小和布局，不能空荡荡。
- 生成结果只显示结果本身、操作悬停才出现，「改参数重新生成」用宽弹窗。这两项已完成（fd68afc4、f68c83a4），这次不改。

## 我的判断（用户可以改）

- **什么时候算「全屏」**：用窗口宽度判断，不看是不是 macOS 全屏状态。内容区宽度 1280px 及以上就用宽布局，所以最大化和 macOS 全屏都算。原因：在大显示器上把窗口拉大但不全屏，同样会空荡。阈值来回切换时加一点滞后（比如放大到 1280 才切宽，缩到 1240 以下才切回），免得在边界上闪。
- **图标栏**：宽 80px，从上到下依次是：
  - macOS 红绿灯留位（约 40px 高，可拖动）、Ofox 标志；
  - 五个页面图标，图标下面带小字。
  - 宽度取 80px 有两个原因：
    - 红绿灯按现在的配置（x=14、间距 20px）会占到约 68px，现在顶栏也给它留了 78px。我们不挪红绿灯，所以宽布局不动 Rust。
    - 日文最长的标签「アシスタント」在 10.5px 字号下约 63px 宽，80px 放得下。
    - 万一标签放不下，就截断，鼠标悬停时显示全名。
  - 底部放更新提示（收成一个小圆点或图标）、刷新、设置。
  - 图标用 lucide。当前页高亮。
  - 键盘操作和现在顶栏的 tab 一样。
- **助手的对话列表**：直接用现有的 `AssistantSidebar`，宽约 260px，紧贴图标栏，背景和图标栏同色，没有外框。收起状态与窄布局共用同一个设置。
- **宽布局的对话区**：
  - 去掉圆角外框和灰底，直接铺白底。
  - 顶部一行：左边是收起列表的按钮和模型选择，右边是「⋯」。这一行可拖动窗口。
  - 对话标题：
    - 列表展开时，顶部不显示标题，当前对话在列表里高亮。
    - 列表收起时，收起按钮右边显示小号标题，否则看不出当前是哪个对话。
  - 重命名：「⋯ → 重命名」或双击顶部标题，会在顶部这一行出现编辑框（复用 `InlineRename`）。编辑期间即使列表展开，也显示这个编辑框。窄布局的重命名方式不变。
  - 消息列居中，宽度随对话区变化，不固定：
    - 最窄 840px，按对话区约 72% 加宽，最宽 1040px（`clamp`）；
    - 输入框和消息列同宽，浮在底部。
    - 这样在 1512px 的笔记本全屏、1920 和 2560 的外接屏最大化时，两边留白都不超过对话区的 15% 左右，也不会因为太宽而难读。
- **放大多少**：宽布局下助手页的字号整体大一档：
  - 回复正文 13→15px，说明文字 11→12px；
  - 图标按钮 26→30px，输入框最小高度加大，列表行高加大；
  - 做法：把字号和尺寸做成 CSS 变量，在宽布局的助手页上换成大一号的值。窄布局的值保持不变。
- **新对话的空白页**：宽布局下输入框放在页面中间偏上，场景卡排在下面（像 ChatGPT 首页）；发出第一句后输入框回到底部。窄布局不变。

## 交给实现者

- 图标的具体选择、动画、阴影、颜色深浅，只要和现有的 magpie 风格（`bg-canvas`、`border-line`、`rounded-ctl` 这些）一致。
- 宽窄判断放在哪一层（建议在 shell 层提供一个 `layout: "narrow" | "wide"`，各页面读它），以及阈值和滞后的具体数值。
- CSS 变量的命名和组织。
- 哪些组件需要拆分才能在两种布局下复用，前提是窄布局的 DOM 结构和样式不变，现有测试照常通过。

## 怎么验收

- 单测：宽窄切换（模拟窗口宽度变化）时，导航在顶栏和图标栏之间移动，当前页、草稿、对话列表收起状态都保留；图标栏的导航有正确的 tab/tabpanel 关系。
- 在 Chrome 页面里按 1000px、1512px、1920px 三种宽度，浅色和深色各截一次图对比：
  - 窄布局和改之前像素一致；
  - 宽布局在列表展开和收起时都没有大片空白。
- 本机试用：macOS 全屏、最大化、普通窗口来回切换；红绿灯不压内容，窗口能拖动。Windows 由 CI 编译，等用户说「提交」后再做 Windows 试用。
